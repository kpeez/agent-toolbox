# run-program

Applies when: a standing project handed to one coordinator session, multi-day, with many stacked PRs, many subagents, and few human turns ("run this whole project", "own this migration until it lands").

You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.

Route here only when the work outlives any single agent. One task driven to a predicate is run-autonomously. One ambitious run that needs a bespoke workflow is figure-it-out. Work one agent could finish inside the session's budget is not a program.

Run it with your own tools. Spawn workers with the host's subagent tool. Keep the program's state in one tracker note in the plans directory (`python3 <plugin-root>/scripts/handoff.py dir`) and in the decision log. Watch each PR with PR and CI event subscriptions when the host has them. Call no scripts, run no polling loops, and never relay messages or status between agents.

1-frame-program: State the done predicate as a count, such as all 126 units merged and each verified. Quantify units, effort, and the wall-clock budget. When one agent could finish inside the budget, run run-autonomously instead. Present the framing once. (in-your-own-words, run-autonomously, log-decisions)
2-one-owner-per-pr: One owner per PR is the only writer of its branch and carries the PR from build to merge. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners. In Claude Code, code workers are `swe:daedalus`. (separate-before-serializing-shared-state)
3-fresh-worker-per-task: Give each independent task a fresh worker. Its brief carries everything it needs, including each upstream report it depends on, pasted in full, because workers cannot see their siblings. Run workers in a cloud session or an isolated worktree, unless the work needs this machine: a runtime check through the project's verification skill, local transcripts, a simulator, or auth that exists only here. Match the model to the job per the Subagents section. (orchestrate)
4-sub-coordinator-only-when-wide: Add a sub-coordinator only when one area has many parallel workers. It owns that area's workers and briefs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch. (guard-the-context-window)
5-fork-for-built-state: Fork or resume a worker only when new work needs its built state, such as its checkout, uncommitted changes, or a running process. Message a worker only for a follow-up on the same work. Never message one to check on it, because a message restarts an idle agent.
6-verify-each-pr: Each PR gets a verifier that is not its author, on a different model. The owner merges only on that verifier's pass at the current head. (reviewer agent, prove-it-works)
7-start-with-one-unit: Take one unit through brief, owner, verifier, and merge before you fan out, so a flaw in the brief costs one agent instead of fifty. On near-identical cheap units, the first unit is that test. (sequence-verifiable-units)
8-name-the-evidence: Each brief names the goal, the evidence that proves the work is done (a command and its expected output, a verification-skill check, or an artifact), the paths the worker may and may not write, and the actions it must not take. If you cannot name the evidence, the unit is not scoped yet.
9-read-the-work: Read the diff or the artifact, not only the worker's summary. Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's briefs while its workers run, and fix its instructions when one fails. Send back work that drifts from scope or grows past what was asked. Keep only the fixes that block the program, and park the rest as follow-ups. (prove-it-works)
10-check-live-state: Check a PR's live state with `gh pr view` and `gh pr checks` before you report on it, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope. (babysit-pr)
11-replace-stalled-workers: Stop or replace a worker that stalls or loops. Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same brief after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
12-ask-only-for-decisions: Ask the user only for a real decision or a blocker: an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user. (never-block-on-the-human)

Reply: what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
